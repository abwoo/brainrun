## 六、发现的问题（按严重程度排序）

### 问题 1（必须修）：Pause 后点 RESET，时钟脱同步 —— B6b

- 现象：暂停后点 RESET，界面显示 PLAY — 运行中，但 TIME 永远停在 0.0 s。
  两次复测一致（TIME 0.0 → 0.0 s）。
- 原因：`App.tsx` 的 `handleReset` 只把 React 的 `paused` 置 false，
  没有给 Worker 发 resume；Worker 里的 `paused` 仍为 true，
  时钟一直冻结。属于界面状态与引擎状态脱节。
- 修复建议：RESET 时同时发 resume（或把 paused 状态收进 Worker
  回传的快照做单一事实来源，界面只读快照）。

### 问题 2（必须修）：拖动旋转可能被误判为“按住” —— B2

- 现象：两次拖动旋转（一次 600 ms 慢拖、一次常规拖动）都多出一个
  `hold` 标记；复测的旋转拖动还因此触发了长时间持续输入，
  把全网锁在高活动态（截图 `06-rotated-180.png`：锁定横幅出现、
  全脑变亮、波形平在约 0.5）。
- 原因：按住判定用的是墙钟 `setTimeout(300 ms)`。主线程卡顿时，
  pointermove 事件还没被处理，计时器先触发，`moved` 还是 false，
  于是拖动被当成按住。这是 Phase 3 修过的同一类问题
  （§11.4 修了按住事件的提交路径，但计时器判定本身没改）。
  本机软件渲染下帧间隔以秒计，所以 2/2 复现；真机 GPU 下帧快，
  需要主线程卡顿超过 300 ms 才会触发，概率低，但机制是真实的。
- 修复建议：用指针事件自带的时间戳（`e.timeStamp`）判定点击/按住，
  不要只依赖墙钟计时器；或计时器触发时若已明显晚于阈值，
  放弃启动按住、交由 pointerup 按时间戳判定。
- 顺带证实：锁定检测与恢复路径本身工作正常——锁定横幅、底栏提示
  都正确出现，RESET 能恢复（Phase 2/3 的设计意图得到了验证）。

### 问题 3（上线前复测，不改代码）：D1 / D2 / D4 / D7 需真机 GPU 复测

- 首屏 6.5 秒 / 11.5 秒、点击到下一帧 2.9 秒、0.8 FPS，
  全部是本机软件渲染的数字，不能当成产品的数字。
  真机复测前，不要对外宣称达到 5 秒首屏或 50–60 FPS。

### 问题 4（建议修）：移动低画质模式未实现 —— D5

- 现状：只有 `setPixelRatio(min(devicePixelRatio, 2))`，
  没有低画质开关。移动端或弱 GPU 上没有降级路径。
- 修复建议：加一个画质开关（降像素比 / 降线框 / 降快照频率），
  或按设备像素比与帧率自动降级。

### 小问题（不阻塞）

- 波形空状态文字（“点击大脑选择一个脑区”）贴在顶部网格线上，
  可读但略挤；移到图表中央更干净。

## 九、两个必修 bug 的修复（验收后、Round 1 前）

### Bug 1 — B6b：Pause 后点 RESET，时钟脱同步（已修，retest 验证通过）

- 根因（以读到的代码为准）：`app/src/App.tsx` 的 `handleReset` 只把
  React 的 `paused` 置 false、调 `sim.reset()`，从没给 Worker 发
  resume；而 `app/src/worker/simWorker.ts` 的 `reset` 分支只调
  `sim.reset()`，不碰 Worker 里的 `paused` 标志，于是 Worker 一直停着。
- 修法（选了“Worker 的 reset 分支同时把 paused 置 false”，不改
  App.tsx）：paused 只活在 Worker 里，快照把它回传、界面只读快照
  镜像它（App 已有 `setPaused(s.paused)`），RESET 应恢复“确定性初始
  状态 + 继续运行”；在 App 侧再发 resume 会留下两个事实来源。
  改动只在 `simWorker.ts` 的 `reset` case + 文件头注释。
- 回归检查：`tests/phase5/retest.py` 的 B6b 一节已扩展为完整循环——
  Pause→RESET 时钟恢复且按钮显示“运行中”→再 Pause 时钟冻结→再
  Resume 时钟推进。实测：TIME 1.0 → 2.3 s（RESET 后）、4.0 → 4.0 s
  （再 Pause）、4.0 → 5.1 s（再 Resume）。

### Bug 2 — B2：拖动旋转误判为“按住”（已修，经历两轮返工）

- 根因（以读到的代码为准）：`app/src/components/BrainScene.tsx`
  里按住判定用墙钟 `setTimeout(300 ms)` + 处理时的 `moved` 标志；
  主线程卡顿时计时器在已入队、尚未处理的 pointermove 之前触发，
  `moved` 仍是 false。
- 第一版修法（失败，Round 1 旧轮次已证实）：计时器触发时不直接启动
  按住，先让出一个任务轮次（`setTimeout(recheckHold, 0)`）再复核。
  实测证明此路不通——探针显示，一次 600 ms 拖动的第一个 move 事件
  时间只比按下晚 110 ms，却在约 900 ms 后才被处理；指针事件按帧
  投递、每帧只来一个，而计时器与二次确认都是任务，跑在下一帧的
  输入投递之前，复核时 `moved` 永远是 false；而且多出的一跳把真正
  的按住启动推迟到评估任务之后，反而让 B3 在卡顿下丢掉按住
  （P 读数为 0）。该轮次 acceptance B2、B3、S2、C2、D4、D7 均失败。
- 第二版修法（时间戳撤回，半程有效）：计时器到时直接启动按住；
  启动之后第一个被处理的 pointermove 若用事件时间戳证明拖动在按住
  启动之前就已开始，立即撤回（停输入、删 `simClient` 的 hold 标记，
  新增 `SimClient.retractHold()` + `App.handleHoldRetract` +
  `BrainScene onHoldRetract`）。慢速拖动两项全过，但普通拖动仍锁网：
  误判窗口约 900 ms，53 号脑区 900 ms 持续输入就锁网（75 号不锁，
  与节点连接强度有关）——窗口本身已逼近锁网阈值，撤回不够快。
- 最终修法（三层，缺一不可，`BrainScene.tsx` + `simClient.ts` +
  `App.tsx`）：
  1. 第一道防线是 `pointerrawupdate`：原始指针更新不合并、不按帧投递，
     实测处理延迟 < 1 ms（同一输入的 pointermove 要等下一帧，约 1 s
     后才到）。任何原始更新只要位移超 6 px 就立刻视为拖动、取消待定
     的按住计时器——拖动一动，按住就不会启动。处理函数
     `notePointerPosition()` 只做标志与计时器操作，不做拾取（原始
     更新频率很高，必须保持廉价）；不支持该事件的浏览器自然走不到
     这层，靠下面两层兜底。
  2. 计时器到时直接启动按住，不再插二次确认——启动任务在 300 ms 时
     入队，保证真正的按住在松开前一定启动、一定被读到（B3）。
  3. 兜底是时间戳撤回（第二版的机制保留）：启动之后，第一个被处理
     的 pointermove（含被合并的中间事件，用 `getCoalescedEvents()`）
     若事件时间早于按住启动的 `performance.now()` 时刻，立即撤回。
     真正的“按住后拖动”不受影响（那时移动事件晚于按住启动）。
- 实测（探针）：两拖动全程 maxE 保持基线 0.019、零标记、零锁定——
  按住根本没启动。retest B2 两项：慢速拖动与普通拖动均“无标记、
  max|P|=0.0、locked=False”。
